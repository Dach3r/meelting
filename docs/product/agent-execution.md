# Agent execution

> **Status:** Phase 3 built in its first cut (`AgentRun`: "Ask", execution with persisted states, streaming, retries, cancellation and expiry at startup, for the five catalog providers) and the "AI providers" screen in Settings; daily limits and Phase 5 (tasks with worktree and tools) are still planned. Behavior ported from the Rails product and extended with streaming, local providers and cancellation. Decisions in [decisions.md](decisions.md); approved technical design in [agent-run.md](../architecture/agent-run.md).

**Problem:** the user has agents and rooms, but the agents do nothing.
**Goal:** let the user direct an instruction to an agent in a room and receive its response, generated by an AI provider (cloud or local), asynchronously, persistently, cancellably and observable live. In a second stage, let the agent work on a real repository inside an isolated worktree.
**User story:** As a workspace owner, I want to ask an agent for a task inside a room, so I get a result and see it arrive while it is generated.

## Scope and exclusions

**Includes (Phase 3)**
- Agent picker in the composer ("Ask"): empty is a normal message; with an agent it is a directed instruction.
- Asynchronous execution as a `tokio` task, with visible states (`queued`, `running`, `succeeded`, `failed`) and the agent's response as a persistent message.
- **Token streaming** to the UI through Tauri events.
- **Five providers, those of the real catalog** (approved decision D9): Anthropic (Messages API), OpenAI (Responses API), Groq (OpenAI-compatible Chat Completions) in the cloud, and Ollama (`localhost:11434`) and LM Studio (`localhost:1234`) locally, both with OpenAI-compatible Chat Completions. Each agent uses the provider and model configured for it. No DeepSeek, MiniMax or a generic `local` in this phase.
- Provider and model catalog in `llm.yml`; keys are stored in the OS keychain.
- Errors, bounded retries, timeouts, idempotency, **cancellation** and token logging.
- Optional daily limits per workspace (proposed for after the first cut of `AgentRun`, A10).

**Includes (Phases 4–5)**
- Tasks with an isolated `git worktree`, agent tools confined to the worktree and human approvals. See [Tools and approvals](#tools-and-approvals).

**Excludes (Phase 3)**
- Task delegation between agents, external integrations. Coordinated conversation between agents and mentions (`@agent`) are proposed for after this phase, in Track R ([voice-meetings.md](voice-meetings.md)).
- Credits, billing and cost calculation in money.
- Manual retry of a failed run.
- Automatic switch of provider or model when one fails.
- `push`, `merge` or modification of the base branch.

## Functional flow
1. The user opens a room with agents and addresses one: mentions it with `@`, names it at the start ("Backend, …"), picks it in "Ask" or continues with the proposed agent ([conversation-engine.md](../architecture/conversation-engine.md#r1-built)).
2. Sends the instruction. The agent appears below with "Queued…".
3. The engine picks up the run: "Thinking…" and, when tokens arrive, "Writing…" with the live text in the same block. If the provider fails transiently, it is retried up to 3 times with the same provider and model.
4. The user can **cancel** the run in progress (`failed` with `error_kind = cancelled`).
5. On success, the response is persisted as the agent's message and the provisional block disappears. Provider, model and tokens are only shown in the response footer.
6. If it fails, the status line explains the reason in the user's language, resolved in the UI from `error_kind`. The user can ask again.
7. If the user leaves the room, the run continues; the response is in the conversation when they return.

## Acceptance criteria
- [x] An instruction can only be directed to an agent participating in the room; an outside agent or one from another workspace fails without saving anything.
- [x] The instruction is saved even if the run fails.
- [x] The response is a persistent message with the agent as author; it is emitted to the UI live.
- [x] States are visible live and survive closing and reopening the app.
- [x] Transient errors are retried (at most 3 attempts, increasing wait, honoring `retry-after`); permanent ones fail immediately with a clear message.
- [x] A run is not processed twice nor creates two responses; there is a single active run per agent and room (unique `client_request_id` and partial index).
- [x] On app start, every orphaned `running` run becomes `failed` with `error_kind = expired`.
- [x] Each agent uses its provider and model; each run keeps the ones it copied when created, even if they are later changed on the agent (D18).
- [x] If a provider's key is missing, only that provider fails with `provider_not_configured`.
- [x] The key never reaches the UI, the logs or the events; prompts and reasoning are not logged.
- [ ] With only the local provider, the app works without an internet connection.
- [x] Cancelling a run ends it and frees the agent.
- [x] Empty states, errors and confirmations in `es` and `en`.

## Business rules
- **Provider and model:** each agent has `provider` and `model` (by default `anthropic` / `claude-sonnet-5-5`), chosen from those in `llm.yml`. Providers without a key can be chosen: the agent shows a warning and the run fails with `provider_not_configured`. If a model leaves the catalog, the agent remains editable and its runs fail with `model_unavailable`. Local providers (`ollama`, `lmstudio`) do not declare models: they are discovered with `GET /v1/models`. The model is always picked from a list, never typed by hand: in the cloud, from `llm.yml`; locally, from the models the runtime returns at that moment. The user can change an agent's provider and model from its edit dialog ("Model" tab, D18); the new pair is validated in the core against the catalog (cloud) or against the models installed in the running runtime (local), and existing runs keep the ones they copied. A local agent whose model is no longer installed remains editable, the edit dialog warns about it and its availability in the room is "Unavailable". Agents with a model retired from the catalog (`gpt-5`, `gpt-5-mini`, `llama-3.3-70b-versatile`) keep their data and their runs fail with `model_unavailable` without calling the provider.
- **Fixed history:** the run copies the agent's `provider` and `model` when created and they are not overwritten.
- **Context:** agent instructions, room name (there is no goal column, D11) and the room's messages prior to the instruction, frozen when the run starts and reused on retries, up to 100 messages and an internal character cap (lower for local models; it is an approximation, not the token window). Other participants' messages are sent with their name.
- **Generation:** response length is controlled with the output-token parameter each provider supports, with the value the catalog declares for the model; other parameters (e.g. `effort`) only if the catalog declares them. No `temperature`. Only the final text is persisted; partial text lives in memory during streaming and reasoning is discarded. `llm.yml` declares the documented output maximum of each cloud model and Meelting requests the lower of that maximum and its internal cap (16 000 in the cloud, 2048 locally).
- **Timeouts:** connection, inactivity (45 s in the cloud as in Rails, more locally) and maximum run duration; these are Meelting's internal limits, not the catalog's. Proposed values in [agent-run.md](../architecture/agent-run.md).
- **Idempotency:** the composer generates a `client_request_id` (UUID) per send and reuses it when retrying that same send; if a run with the same `(room, client_request_id)` already exists, its message and run are returned without creating anything or calling the provider. The id is mandatory, and the same id with another agent or another text returns `client_request_conflict`, instead of the Rails rule that generated a new one ([agent-run.md §3](../architecture/agent-run.md#3-send_instruction-contract-and-idempotency-a2)). If the agent already has an active run in the room, the instruction is rejected with `agent_busy` and nothing is saved.
- **Error messages:** the UI resolves them by `error_kind` (with the provider's name); an unknown one shows the generic message. The provider's text and keys are never shown.
- **Retries:** 3 attempts with increasing wait; the HTTP client uses `max_retries = 0` and only the engine retries.
- **Transient errors:** `rate_limited`, `timeout`, `provider_unavailable`. **Permanent:** `provider_not_configured`, `model_unavailable`, `provider_auth_failed`, `provider_billing`, `provider_rejected`, `content_filtered`, `output_truncated`, `invalid_response`, `context_too_large`, plus `cancelled` and `expired`. A `connection_refused` against `localhost` is `provider_unavailable` and the UI shows "Ollama is not running".
- **Daily limits (optional):** 50 runs and 500 000 tokens in 24 hours, disabled for local providers. Initial protection, not a strict budget. Outside the first cut of `AgentRun`: they need the `settings` table (proposal A10 in [agent-run.md](../architecture/agent-run.md)).
- **Logging:** per run, the provider, model, attempts, input and output tokens (if the provider reports them) and creation, start and end timestamps are stored. The reported model, cache tokens, `finish_reason` and the provider's request id are not stored because nothing uses them yet.
- **Deleting an agent** with messages or runs is not allowed (`agent_has_activity`). **Finishing a room** keeps its runs and messages and cancels the runs in progress.
- **Response length (approved decision D10):** the 4000-character limit applies only to user messages. The agent's response has no character limit; it is bounded by the model's output tokens and the context limits. It is never truncated silently: if the provider cuts the response (length `finish_reason`) the run fails with `output_truncated` and no message is created; if it filters it, with `content_filtered`. The `messages` schema does not change.

## Implications of conversational meetings

> **Proposal, pending.** Nothing in this section replaces the rules above until it is approved. Details in [conversation-engine.md §10](../architecture/conversation-engine.md#10-agentrun-adaptations).

- `AgentRun` remains **independent of audio**: voice consumes the persisted message and voice input arrives as transcribed text.
- **Idempotency with several runs per intervention:** a unique `client_request_id` would prevent an intervention to "Team" from creating several runs (C1 in [conversation-engine.md](../architecture/conversation-engine.md#12-persistence-and-data-model); resolved in [agent-run.md](../architecture/agent-run.md)).
- The prompt is built on `claim`, so each turn sees the previous responses.
- Tokens carry `run_id` and a sequence; on retry the provisional text is reset and voice only uses the final text.
- Possible "pass" outcome (`succeeded` without a message) in team mode: affects the `CHECK`s ported from Rails.
- Cancellation per intervention and per room, in addition to per run.
- The next turn is created by the coordinator, never by the previous run.
- "Change model" is an explicit user action in the agent's edit dialog (D18); it is never automatic when a provider fails.

## API keys

- Stored in the OS keychain under the service `meelting` and the name `<workspace_id>/<provider>`, so each workspace has its own keys. There is no table: whether a provider is configured is read from the keychain (D26).
- Managed in the **AI providers** screen («Proveedores de IA»), its own item in the sidebar rail. The two groups sit side by side in their own panels (stacked on narrow windows), each provider in its own card with a status dot (success colour when connected or running, error colour on a problem):
  - **In the cloud** (Anthropic, OpenAI, Groq): summary "N of 3 configured" and one row per provider with "Add key", or, once configured, "Check connection", "Replace" and "Delete". Adding or replacing expands a password field (no autocomplete or spell check) with "Verify and save"; the field is emptied after every attempt.
  - **On this computer** (Ollama, LM Studio): read only. They need no key; the row shows whether the runtime is running at the catalog address and how many models it has, lists the installed model names, with "Detect again". Their URL is not editable.
- **Verification before saving:** a minimal request (fixed instruction, first model of the provider in the catalog, `max_output_tokens: 16`) to the catalog's `base_url`, through the same adapter the engine uses. The UI cannot choose the URL. Result:
  - `verified` (a reply, including one cut by the 16-token cap or filtered): the key is saved.
  - `rejected` with the reason (`provider_auth_failed`, `provider_billing`, `model_unavailable`, `provider_rejected`): not saved.
  - `offline` (no connection could be made): not saved; the provider is marked as without connection, as after a failed run.
  - `provider_busy` (5xx, rate limit, timeout or an invalid response): not saved; try again later.
  - When replacing, the new key only overwrites the previous one if it is verified; otherwise the previous one is kept and the screen says so.
- **Row states:** not configured; configured (not checked in this session); connected (last check succeeded); no internet connection (the last request to the provider could not connect); not responding; key rejected (a check of the stored key failed, which never deletes it).
- Opening the screen makes no cloud request: "Check connection" re-verifies the stored key on demand.
- Deleting asks for confirmation, does not touch agents (they show "Needs setup" and nothing switches provider or model) and a run in progress fails on its next attempt with `provider_not_configured`.
- The key is never shown again: only its last 4 characters. It does not travel in results, errors, events or logs, and the UI keeps it only in the field while it is typed. The webview has no generic secret commands: only `list_provider_keys`, `save_provider_key`, `check_provider_key` and `delete_provider_key`, which take the provider and resolve the workspace in the core.

## Tools and approvals

Planned (Phases 4–5); documented with [feature-template.md](feature-template.md) before implementing it.

- Each task has its own branch `meelting/<slug>-<short id>` and `git worktree` inside the app's data directory, never inside the user's repository.
- Tools: `read_file`, `list_dir`, `search`, `write_file`, `edit_file`, `run_command`, `git_status`, `git_diff`, `git_commit`. No `push`.
- `run_command` requires **human approval** showing the exact command (approve once, for the task, or deny), except for a short, reviewable list.
- Mandatory controls: path jail (every path canonicalized inside the worktree), sanitized environment (no keys or `SSH_AUTH_SOCK`), timeout and output limit per command, process tree terminated on expiry.
- Optional Docker as strong isolation; without Docker the app warns that execution is **not isolated**.
- Every call is recorded in `tool_calls` for auditing.

## Known limitations
- **A single external invocation is not guaranteed:** an app shutdown after the provider responded and before saving the result can cause a new call. Idempotency is local.
- Daily limits are not strict under concurrency.
- Reasoning that exhausts `max_output_tokens` fails as `output_truncated`.
- Responses are shown as plain text, without markdown.
- A failed run cannot be retried: the instruction must be sent again.
- Each provider's parameters are pinned with `wiremock` tests. With a real provider only Ollama has been verified (including token usage in streaming). Anthropic, OpenAI, Groq and LM Studio await their optional real tests (`#[ignore]`, with the key in an environment variable): in particular, `Bearer` authentication and the `2026-10-21` version of Anthropic, whether Groq accepts `stream_options`, and the shape of LM Studio's usage chunk.
- The "without an internet connection" check with only a local provider has not yet been done with the network disabled (the app does not call the cloud with local agents).

**Priority:** Must Have
**Success metric:** percentage of rooms with at least one `succeeded` run, rate of `failed` runs by `error_kind` and provider, tokens per run and provider.
